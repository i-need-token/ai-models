# 设计原则与陷阱

构建和维护 AI 模型目录过程中积累的经验教训。每条陷阱描述的是可能反复出现的通用模式，而非一次性 bug。

## 架构

### 通过设计防止编造，而非仅靠 Lint

**陷阱**：依赖事后 lint 规则来捕获抓取函数中的硬编码数据。

**问题**：Lint 规则是建议性的 — AI 代理可以绕过它们。当函数有自由度返回任意 `Model` 对象时，除了规则说"不要"之外，没有任何东西阻止硬编码。

**原则**：使用类型约束使编造在结构上不可能。Pipeline 步骤的窄输出类型（`discover()` → 只有 ID，`extractPricing()` → 只有定价）使得硬编码无关数据在结构上不可能。声明式规则更进一步 — AI 只能定义 CSS 选择器、正则表达式和 JSONPath 表达式，不能写任意代码。

### 抓取函数必须是纯数据函数

**陷阱**：在单个函数中混合数据获取、转换和文件 I/O。

**问题**：没有明确的返回类型，难以测试，难以组合，文件写入逻辑在各供应商间重复。

**原则**：抓取函数返回结构化数据 (`{ provider, models }`)。由一个全局编排脚本处理所有文件 I/O。这分离了"获取数据"和"持久化数据"，使抓取函数无需触碰文件系统即可测试。

### 模型发现必须是动态的

**陷阱**：在抓取函数中硬编码模型 ID 列表。

**问题**：新模型不会出现，直到人工更新列表。已移除的模型会残留，直到手动删除。违背了自动化数据采集的目的。

**原则**：每个抓取函数必须包含从供应商数据源获取模型列表的**发现步骤**。只有过滤规则 (前缀、排除模式) 可以硬编码 — 模型 ID 本身绝不可以。

### 数据必须来自第一方来源

**陷阱**：从第三方聚合器复制数据 (如 models.dev、OpenRouter 上其他供应商的模型卡片)。

**问题**：第三方数据可能过时、不准确或不完整。无法直接追溯责任 — 错误无法定位到供应商自身的文档。

**原则**：所有数据必须来自供应商自身的 API、网站或官方文档。不从第三方聚合器复制。

### 推理平台有严格的审查标准

**陷阱**：添加任何提供 LLM 模型的平台，而不验证数据可访问性和定价模型。

**问题**：许多平台看起来像推理供应商，但实际上是路由器（无自有定价）、GPU 租赁服务（无按 token 定价）或企业平台（需要认证）。添加它们浪费精力并产生低质量数据。

**原则**：推理平台必须具备 (1) 无需认证的公开 API，(2) USD/CNY/EUR 按 token 定价，(3) 第一方数据。路由器/聚合器、GPU 云、信用点平台和需认证的 API 都被拒绝。

### 包含 "/" 的模型 ID 必须扁平化

**陷阱**：直接将包含 "/" 的模型 ID 用作 YAML 文件名。

**问题**：写入 `models/owner/model.yaml` 时出现文件系统 ENOENT 错误 — "/" 创建了不存在的子目录。

**原则**：将模型 ID 中的 "/" 替换为 "--"（如 `meta-llama/llama-3.1-8b` → `meta-llama--llama-3.1-8b`）。这避免了文件系统路径问题，同时保持 ID 可识别。

### 浮点定价必须四舍五入

**陷阱**：将按 token 价格转换为按百万 token 价格时产生浮点噪声（如 `0.19999999999999998` 而非 `0.2`）。

**问题**：YAML 文件包含难看的浮点伪影。价格看起来不准确，即使底层计算是正确的。

**原则**：将按 token 转换为按 M token 时，使用 `Math.round(value * 1e6) / 1e6` 四舍五入到 6 位小数，消除浮点噪声。

## 数据完整性

### 绝不编造缺失数据

**陷阱**：当模型数据缺失时使用回退值 (如 `detail?.context || 200_000`)。

**问题**：缺失数据的模型以虚假值出现在目录中。无法检测哪些模型数据不完整。破坏数据完整性 — 使用者信任这些值。

**原则**：当必需数据缺失时，跳过该模型并记录警告。准确数据少一些，也比编造数据多一些好。

### 包含已废弃模型，排除已退役模型

**陷阱**：将已废弃模型从目录中完全排除。

**问题**：仍在使用已废弃模型的用户找不到它们。无法区分"不在目录中"和"已废弃但仍可通过 API 访问"。

**原则**：已废弃模型 (仍可访问，不推荐使用) 以 `deprecated: true` 标记纳入。已退役模型 (不再可访问) 排除。这保持了目录的完整性，同时标明了状态。

### 尽可能从数据源提取特性标志

**陷阱**：对所有模型硬编码能力标志 (如 `reasoning: true`)。

**问题**：如果未来模型不支持某特性，会被错误标记。违反第一方数据原则。

**原则**：尽可能从数据源提取特性标志。当数据源不暴露逐模型特性时，硬编码并记录为已知限制。

## HTML 解析

### 将搜索范围限定在卡片边界内

**陷阱**：在模型链接周围的固定字符窗口内搜索属性 (如 "Deprecated")。

**问题**：相邻卡片的属性泄漏到搜索窗口中，导致误报。窗口大小是任意的、脆弱的。

**原则**：始终将搜索范围限定在当前卡片元素内。找到卡片边界 (如起始 `<a>` 标签到其闭合 `</a>`)，只在边界内搜索。

### 使用精确的 404 检测

**陷阱**：在 HTML 中任意位置搜索 "404" 来检测缺失页面。

**问题**："404" 出现在无关内容中 (如速率限制文档提及 "404 errors")。有效页面被错误地视为缺失。

**原则**：检查 `<title>` 标签是否包含 "Page not found" 或类似内容，而不是在整个 HTML 中搜索 "404"。

### 将废弃检测限定在模型头部

**陷阱**：在模型详情页任意位置检查 "Deprecated"。

**问题**：单个快照可以被废弃，而模型本身仍然活跃。抓取器无法区分"模型已废弃"和"模型有已废弃的快照"。

**原则**：只在模型头部区域 (Snapshots 区域之前) 检查废弃徽章。快照级别的废弃状态在每个快照条目中单独追踪。

### 使用特性区域，而非通用字符串匹配

**陷阱**：通过 `html.includes("reasoning.effort")` 或类似通用字符串检测能力。

**问题**：导航链接、搜索文本和无关内容会匹配该字符串。非推理模型被错误标记。

**原则**：使用页面的结构化特性区域。在特性列表模式中检查特定特性名称。

### 提取所有匹配，而非仅第一个

**陷阱**：使用 `html.match(pattern)` 只返回第一个匹配。

**问题**：提取重复结构 (如快照、定价层级) 时，只捕获第一个，其余被静默丢弃。

**原则**：使用 `matchAll` 或全局正则循环提取所有匹配项。

## Schema 设计

### 保持模态类型同步

**陷阱**：在 `ModelModality` 中添加了模态，但忘记更新 `pricing.ts` 中的 `Modality` 和 `schemas.ts` 中的 `ModalitySchema`。

**问题**：类型系统不一致。无法为新模态表达按模态定价。

**原则**：在 `ModelModality` 中添加新模态时，始终检查 `pricing.ts` 中的 `Modality` 和 `schemas.ts` 中的 `ModalitySchema` 是否也需要更新。

### 非所有模型类型都有的字段设为可选

**陷阱**：将 `limit`、`knowledge` 或能力字段在 schema 中设为必填。

**问题**：图像、嵌入和审核模型没有上下文窗口或知识截止日期。schema 无法表示这些模型类型。

**原则**：当字段不适用于所有模型类型时设为可选。`Pricing` 联合类型应有所有定价结构的变体 (token、按图像、按秒、免费)。

### Family 是宽泛分组，非版本化名称

**陷阱**：在 family 名称中包含版本号 (如 `gpt-5-codex` 而非 `gpt-codex`)。

**问题**：Family 粒度过细 — 同一变体的不同代际被分到不同的 family，失去了作为宽泛分组的意义。

**原则**：Family 代表一个宽泛的系列，而非特定代际。推导 family 时去掉版本号 (如 `gpt-5-codex` → `gpt-codex`、`claude-opus-4` → `claude-opus`)。显示名称匹配供应商官方大小写。

## 数据格式

### YAML 优于 JSON 用于人工可编辑数据

**陷阱**：使用 JSON 存储模型数据文件。

**问题**：JSON 可读性较差，不支持注释，更冗长。

**原则**：使用 YAML 作为源格式 — 更可读，支持注释，同样可被机器解析。

### 快照使用继承，而非复制

**陷阱**：每个带日期的模型 ID 作为独立文件，数据完全重复。

**问题**：大量数据重复。无法知道哪个快照是当前的。更新共享字段需要编辑每个快照文件。

**原则**：模型 ID 是稳定名称。快照嵌套在模型文件中并使用继承 — 只需指定不同的字段。

## 定价提取

### 编写 HTML 抓取器前先检查替代数据格式

**陷阱**：用 DOM 选择器和脆弱的 CSS 假设解析供应商 HTML。

**问题**：HTML 结构变化会破坏抓取器。折叠的空白、动态类名和嵌套元素使提取不可靠。

**原则**：编写 HTML 抓取器前，检查供应商是否提供 JSON、markdown、YAML 或其他结构化格式。这些更稳定、更容易解析。只有在没有结构化替代方案时才回退到 HTML 解析。

### 不要假设解析表的固定列索引

**陷阱**：用硬编码的列索引 (如 `cols[2]`) 提取特定值。

**问题**：不同章节或供应商的表可能有不同的列数。固定索引在结构变化时取到错误的列。

**原则**：用 `cols[cols.length - 1]` 取最后一列，或按表头文本识别列。绝不硬编码列索引。

### 两步提取：先匹配块边界，再提取内部值

**陷阱**：用单个正则从一个分隔块中提取多个值。

**问题**：只捕获第一个和最后一个值，中间值被静默丢弃。

**原则**：先匹配外层块边界，再从内部提取所有值。这样可以处理块中任意数量的值。

### 同一供应商内定价模型可能不同

**陷阱**：假设同一类别的模型共享相同的定价结构。

**问题**：同一供应商内，有些模型按 token 定价，有些按图片、按秒或按请求定价。有些有阶梯或按模态拆分的定价。假设单一结构会导致错误分类。

**原则**：逐模型独立解析定价。不要按模型家族批量假设定价类型。注意这些变体：

- 单位定价 (按图片/视频/请求) vs token 定价
- 阶梯定价 (上下文长度阈值、分辨率阶梯)
- 模态拆分定价 (text vs audio vs image 不同费率)
- 混合定价 (token 输入 + 按单位输出) — 类型系统可能不支持

### 每个免费定价的模型都必须核实

**陷阱**：找不到定价数据时静默默认为免费。

**问题**：缺少定价数据的付费模型显示为免费。这是严重的数据准确性错误，会误导用户关于成本的判断。

**原则**：抓取后，列出所有免费定价的模型，逐一对照供应商定价页核实是否真的免费。如果付费模型没有定价，说明抓取器有 bug。

### 不要假设快照与父模型共享定价

**陷阱**：假设快照总是继承父模型的定价。

**问题**：一些列为快照的变体有自己独立的定价。作为快照处理意味着它们没有定价数据。

**原则**：解析每个模型后，检查是否有快照有独立定价。如果有，将它们提升为独立模型。

## 正则与命名

### 正则交替顺序：长的/更具体的替代项必须在短的之前

**陷阱**：在正则交替中写 `pro|pro-tts`。

**问题**：短的替代项先匹配，长的永远匹配不到。这导致复合模型变体的 name/family 推导错误。

**原则**：始终从最长/最具体到最短排列正则交替。用所有可能的输入测试，确认没有替代项被遮蔽。

### Name 和 Family 推导必须处理所有模型 ID 模式

**陷阱**：在 name 推导中硬编码版本号或只处理最常见的命名模式。

**问题**：供应商发布新版本时硬编码名称出错。复合变体被简单正则漏掉。版本标记 (如 `-preview-`) 之后出现的后缀可能无法被主正则捕获。

**原则**：编写 name/family 推导前，先从数据源收集所有模型 ID 并分类命名模式。从模型 ID 中动态提取版本号。为主正则无法捕获的后缀添加后处理。用完整列表测试。

## 验证

### 模型数量必须与官方列表一致

**陷阱**：信任抓取器输出数量而不交叉核对。

**问题**：废弃模型虚增数量、仅定价页模型遗漏、有独立定价的快照未提升。每个问题都会改变数量。

**原则**：抓取后，将模型数量与供应商官方列表对比。如果不匹配，调查原因。常见原因：

- 废弃/停运模型未过滤
- 仅在定价页上 (无详情页) 的模型遗漏
- 有独立定价的快照未提升为独立模型
- 隐藏在其他导航路径后的模型

### 迭代代码审查直到干净 — 一次永远不够

**陷阱**：运行一次代码审查就宣布爬虫完成。

**问题**：Google 爬虫花了 9 轮代码审查才发现所有问题。每轮都发现前一轮遗漏的 1-5 个问题 — 正则表达式顺序、定价类型不匹配、缺失模型属性、README 漂移、解析边界情况。

**原则**：构建爬虫后，至少运行 3 轮代码审查。继续直到某轮发现零问题。每轮应审查完整爬虫和输出 YAML 文件样本。

## JS 包与路由器/聚合器平台

### CSR 渲染的定价页面可能将数据嵌入 JS 包

当定价页面是客户端渲染的（React/Next.js）时，定价数据通常嵌入在公开可访问的 JavaScript 块中，而非从单独的 API 获取。这是有效的第一方数据源：

- **nano-gpt**：定价数据嵌入在 `30244-*.js` 块中，包含 `inputRate`/`outputRate` 按 token 值和利润率乘数 `R=1.7`。带有 `/R` 后缀的条目存储成本价（成本 = 值 / R），但 `/R` 之前的值就是客户价格。
- **Azure OpenAI**：定价页面是 CSR 渲染的；通过浏览器自动化提取数据。
- **Google Vertex AI**：与 Azure 相同 — CSR 渲染的定价页面通过浏览器抓取。

**关键洞察**：可以通过解析定价页面的 HTML 中的 `<script src="...">` 标签找到 JS 包 URL。包 URL 通常包含内容哈希（例如 `30244-66042ba6af5cbcfb.js`），每次部署时都会更改。

### 具有按 token 定价的路由器/聚合器平台是可接受的

像 OpenRouter 和 nano-gpt 这样的平台是路由器/聚合器，不生产自己的模型，但它们确实拥有可从第一方来源访问的按 token 定价数据：

- **OpenRouter**：公开 API（`/api/v1/models`）返回 300+ 个模型及按 token USD 定价。
- **nano-gpt**：公开 API 获取模型列表 + JS 包获取按 token USD 定价（555 个模型）。

这些平台被视为推理平台，而非被拒绝为“只是路由器”，因为它们提供可验证的第一方按 token 定价数据。
