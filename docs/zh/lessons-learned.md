# 设计原则与陷阱

构建和维护 AI 模型目录过程中积累的经验教训。每条陷阱描述的是可能反复出现的通用模式，而非一次性 bug。

## 架构

### 抓取函数必须是纯数据函数

**陷阱**：在单个函数中混合数据获取、转换和文件 I/O。

**问题**：没有明确的返回类型，难以测试，难以组合，文件写入逻辑在各供应商间重复。

**原则**：抓取函数返回结构化数据 (`{ provider, models }`)。由一个全局编排脚本处理所有文件 I/O。这分离了"获取数据"和"持久化数据"，使抓取函数无需触碰文件系统即可测试。

### 模型发现必须是动态的

**陷阱**：在抓取函数中硬编码模型 ID 列表。

**问题**：新模型不会出现，直到人工更新列表。已移除的模型会残留，直到手动删除。违背了自动化数据采集的目的。

**原则**：每个抓取函数必须包含从供应商数据源获取模型列表的**发现步骤**。只有过滤规则 (前缀、排除模式) 可以硬编码 — 模型 ID 本身绝不可以。

### 数据必须来自第一方来源

**陷阱**：从第三方聚合器复制数据 (如 models.dev、OpenRouter 上其他供应商的模型卡片)。

**问题**：第三方数据可能过时、不准确或不完整。无法直接追溯责任 — 错误无法定位到供应商自身的文档。

**原则**：所有数据必须来自供应商自身的 API、网站或官方文档。不从第三方聚合器复制。

## 数据完整性

### 绝不编造缺失数据

**陷阱**：当模型数据缺失时使用回退值 (如 `detail?.context || 200_000`)。

**问题**：缺失数据的模型以虚假值出现在目录中。无法检测哪些模型数据不完整。破坏数据完整性 — 使用者信任这些值。

**原则**：当必需数据缺失时，跳过该模型并记录警告。准确数据少一些，也比编造数据多一些好。

### 包含已废弃模型，排除已退役模型

**陷阱**：将已废弃模型从目录中完全排除。

**问题**：仍在使用已废弃模型的用户找不到它们。无法区分"不在目录中"和"已废弃但仍可通过 API 访问"。

**原则**：已废弃模型 (仍可访问，不推荐使用) 以 `deprecated: true` 标记纳入。已退役模型 (不再可访问) 排除。这保持了目录的完整性，同时标明了状态。

### 尽可能从数据源提取特性标志

**陷阱**：对所有模型硬编码能力标志 (如 `reasoning: true`)。

**问题**：如果未来模型不支持某特性，会被错误标记。违反第一方数据原则。

**原则**：尽可能从数据源提取特性标志。当数据源不暴露逐模型特性时，硬编码并记录为已知限制。

## HTML 解析

### 将搜索范围限定在卡片边界内

**陷阱**：在模型链接周围的固定字符窗口内搜索属性 (如 "Deprecated")。

**问题**：相邻卡片的属性泄漏到搜索窗口中，导致误报。窗口大小是任意的、脆弱的。

**原则**：始终将搜索范围限定在当前卡片元素内。找到卡片边界 (如起始 `<a>` 标签到其闭合 `</a>`)，只在边界内搜索。

### 使用精确的 404 检测

**陷阱**：在 HTML 中任意位置搜索 "404" 来检测缺失页面。

**问题**："404" 出现在无关内容中 (如速率限制文档提及 "404 errors")。有效页面被错误地视为缺失。

**原则**：检查 `<title>` 标签是否包含 "Page not found" 或类似内容，而不是在整个 HTML 中搜索 "404"。

### 将废弃检测限定在模型头部

**陷阱**：在模型详情页任意位置检查 "Deprecated"。

**问题**：单个快照可以被废弃，而模型本身仍然活跃。抓取器无法区分"模型已废弃"和"模型有已废弃的快照"。

**原则**：只在模型头部区域 (Snapshots 区域之前) 检查废弃徽章。快照级别的废弃状态在每个快照条目中单独追踪。

### 使用特性区域，而非通用字符串匹配

**陷阱**：通过 `html.includes("reasoning.effort")` 或类似通用字符串检测能力。

**问题**：导航链接、搜索文本和无关内容会匹配该字符串。非推理模型被错误标记。

**原则**：使用页面的结构化特性区域。在特性列表模式中检查特定特性名称。

### 提取所有匹配，而非仅第一个

**陷阱**：使用 `html.match(pattern)` 只返回第一个匹配。

**问题**：提取重复结构 (如快照、定价层级) 时，只捕获第一个，其余被静默丢弃。

**原则**：使用 `matchAll` 或全局正则循环提取所有匹配项。

## Schema 设计

### 保持模态类型同步

**陷阱**：在 `ModelModality` 中添加了模态，但忘记更新 `pricing.ts` 中的 `Modality` 和 `schemas.ts` 中的 `ModalitySchema`。

**问题**：类型系统不一致。无法为新模态表达按模态定价。

**原则**：在 `ModelModality` 中添加新模态时，始终检查 `pricing.ts` 中的 `Modality` 和 `schemas.ts` 中的 `ModalitySchema` 是否也需要更新。

### 非所有模型类型都有的字段设为可选

**陷阱**：将 `limit`、`knowledge` 或能力字段在 schema 中设为必填。

**问题**：图像、嵌入和审核模型没有上下文窗口或知识截止日期。schema 无法表示这些模型类型。

**原则**：当字段不适用于所有模型类型时设为可选。`Pricing` 联合类型应有所有定价结构的变体 (token、按图像、按秒、免费)。

### Family 是宽泛分组，非版本化名称

**陷阱**：在 family 名称中包含版本号 (如 `gpt-5-codex` 而非 `gpt-codex`)。

**问题**：Family 粒度过细 — 同一变体的不同代际被分到不同的 family，失去了作为宽泛分组的意义。

**原则**：Family 代表一个宽泛的系列，而非特定代际。推导 family 时去掉版本号 (如 `gpt-5-codex` → `gpt-codex`、`claude-opus-4` → `claude-opus`)。显示名称匹配供应商官方大小写。

## 数据格式

### YAML 优于 JSON 用于人工可编辑数据

**陷阱**：使用 JSON 存储模型数据文件。

**问题**：JSON 可读性较差，不支持注释，更冗长。

**原则**：使用 YAML 作为源格式 — 更可读，支持注释，同样可被机器解析。

### 快照使用继承，而非复制

**陷阱**：每个带日期的模型 ID 作为独立文件，数据完全重复。

**问题**：大量数据重复。无法知道哪个快照是当前的。更新共享字段需要编辑每个快照文件。

**原则**：模型 ID 是稳定名称。快照嵌套在模型文件中并使用继承 — 只需指定不同的字段。
